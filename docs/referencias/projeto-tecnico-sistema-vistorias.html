Projeto Técnico

Sistema web/PWA offline-first para gestão de vistorias técnicas, destinado inicialmente a um único engenheiro e seus clientes.

V1 • Monólito modular • Offline-first • Storage privado

1. Visão geral

O sistema tem como objetivo apoiar o ciclo completo de uma vistoria: divulgação do serviço, solicitação pelo cliente, agendamento, execução em campo, coleta de dados e fotografias, sincronização posterior, geração do laudo em PDF e disponibilização dos documentos ao cliente.

Premissa central: a etapa de vistoria deve funcionar sem conexão com a Internet. A conectividade será usada para sincronizar os dados quando estiver disponível.

3. Personas

👷 Engenheiro

Objetivo: receber solicitações, organizar a agenda, executar vistorias em campo e produzir/entregar laudos.

  • Usa principalmente o celular.
  • Pode trabalhar em locais sem sinal.
  • Precisa registrar muitas fotografias.
  • Precisa proteger dados pessoais e documentos.
  • Valoriza agilidade e baixa fricção.

👤 Cliente

Objetivo: solicitar uma vistoria, acompanhar o atendimento e receber os documentos finais.

  • Acessa pelo celular ou computador.
  • Não precisa de um painel administrativo.
  • Deve visualizar somente seus próprios dados e documentos.
  • Precisa de acesso simples ao laudo.

Frontend

PWA, interface mobile-first, câmera, IndexedDB, fila local e sincronização.

Backend

API, autenticação, autorização, regras de negócio, URLs temporárias e geração de documentos.

Banco

PostgreSQL para dados estruturados e referências dos arquivos.

Storage

Bucket privado para fotografias, PDFs, ARTs e demais documentos.

7. Armazenamento e segurança

7.1 Estratégia

  • Fotos são capturadas e persistidas localmente durante a vistoria.
  • Fotos podem ser redimensionadas/comprimidas no dispositivo antes da sincronização.
  • O upload para o object storage ocorre diretamente, usando autorização temporária emitida pelo backend.
  • O bucket permanece privado.
  • O banco guarda metadados e a chave do objeto, não o arquivo binário.

7.2 Controle de acesso

Usuário autenticado
       ↓
Backend verifica autorização
       ↓
Recurso pertence à vistoria permitida?
       ↓
SIM → gera URL temporária
NÃO → 403 Forbidden
Regra: nunca colocar credenciais permanentes do storage no frontend e nunca confiar em IDs fornecidos pelo cliente para decidir autorização.

ARTEngenheiroUpload controlado → validação → storage privado.
Laudo PDFSistemaGerado no servidor → storage privado.

10. Offline-first

O modo offline é obrigatório na etapa de campo. A aplicação deve persistir dados antes de considerar a operação concluída.

ComponenteResponsabilidade
IndexedDBPersistir dados da vistoria, metadados e referências locais.
Filesystem/Blob localArmazenar temporariamente fotografias e arquivos grandes, conforme a tecnologia escolhida.
Sync QueueRegistrar operações pendentes e permitir retry.
Sync Worker/ServiceDetectar conectividade e executar sincronizações.
IdempotênciaEvitar duplicação quando uma resposta é perdida após o upload.
Regra de conclusão: a aplicação deve informar claramente quantos itens estão sincronizados, pendentes ou com erro. Não se deve apresentar uma vistoria como totalmente sincronizada enquanto existirem arquivos pendentes.

Como referência inicial, pode-se limitar a dimensão da imagem destinada ao sistema/laudo a aproximadamente 2400–3000 px no maior lado e usar JPEG/WebP com qualidade ajustável. Os limites devem ser validados com exemplos reais do engenheiro antes de serem fixados.

15. Geração do laudo

O laudo deve ser produzido a partir de dados estruturados, e não montado manualmente a partir das fotografias. O modelo deve ser versionado para permitir alterações futuras sem invalidar documentos antigos.

  • Identificação do engenheiro.
  • Dados do cliente e imóvel.
  • Objeto e finalidade da vistoria.
  • Data e informações da inspeção.
  • Constatações/checklist.
  • Registro fotográfico.
  • Conclusão.
  • Assinatura.
  • Referência ou anexo da ART.
Assinatura digital: a implementação da assinatura deve ser definida conforme o método e requisitos profissionais/jurídicos adotados pelo engenheiro. O sistema não deve presumir que uma imagem de assinatura equivale a uma assinatura digital qualificada.

16. Observações sobre a V1

  • O sistema é destinado inicialmente a um único engenheiro, mas a modelagem deve evitar acoplamento desnecessário entre usuário e todos os dados.
  • Não implementar multitenancy agora.
  • Não transformar o Google Drive em requisito arquitetural. Caso seja usado, encapsulá-lo atrás de uma abstração de armazenamento.
  • Object storage privado é a opção preferencial para produção.
  • O modo offline deve ser testado em condições reais, incluindo ausência total de sinal, fechamento do aplicativo, reinicialização e retomada de sincronização.
  • Vídeos devem permanecer fora do caminho crítico da V1 até existir uma necessidade concreta.

17. Critérios de aceite da V1

  1. O engenheiro consegue autenticar-se e acessar sua área administrativa.
  2. Um cliente consegue solicitar uma vistoria pelo celular.
  3. O engenheiro consegue configurar horários e confirmar uma solicitação.
  4. Uma vistoria pode ser aberta no celular e executada sem Internet.
  5. Fotos e dados permanecem disponíveis após fechar/reabrir a aplicação.
  6. Ao retornar a conectividade, a sincronização pode ser retomada sem duplicar arquivos.
  7. Arquivos são enviados para storage privado sem expor credenciais permanentes.
  8. O engenheiro consegue gerar um PDF com dados e fotografias da vistoria.
  9. A ART pode ser vinculada à vistoria.
  10. O cliente consegue acessar somente os documentos autorizados.
  11. O sistema informa claramente pendências de sincronização.
